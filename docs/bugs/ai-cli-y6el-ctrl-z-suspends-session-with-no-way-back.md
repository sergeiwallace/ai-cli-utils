## Summary

An accidental Ctrl+Z in a Claude Code session launched by `ai c` froze the pane. Claude Code
printed "Run `fg` to bring Claude Code back" and "ctrl + _ undoes input". Neither `fg` (which the
operator read as `kg`) nor Ctrl+\_ did anything. The only way out was for another session to kill
the process so the launcher restarted it, and that killed every background agent and shell the
session owned.

## Reproduction

A throwaway session generated by `get_engine_script` on a private tmux socket (`tmux -L y6el`)
with a private `XDG_STATE_HOME`, running the real Claude Code 2.1.283. No live session was
touched.

Before Ctrl+Z (pid, ppid, pgid, tpgid, stat, wchan):

```text
688207  688199  688207  688328 SNs  sigsuspend   zsh c-r-y6elrepro.sh                  <- supervisor
688328  688207  688328  688328 SN+  sigsuspend    \_ zsh ... --ai-cli-child-body       <- foreground group
688594  688328  688328  688328 SN+  sigsuspend        \_ zsh ... --ai-cli-child-body   <- watcher subshell
689358  688328  688328  688328 SNl+ ep_poll           \_ claude --dangerously-skip-permissions --name y6elrepro
706625  689358  688328  688328 SNl+ ep_poll               \_ mcp-atlassian ...
```

After `tmux send-keys C-z`:

```text
688207  688199  688207  688328 SNs  sigsuspend       zsh c-r-y6elrepro.sh
688328  688207  688328  688328 TN+  do_signal_stop    \_ zsh ... --ai-cli-child-body
688594  688328  688328  688328 TN+  do_signal_stop        \_ zsh ... --ai-cli-child-body
689358  688328  688328  688328 TNl+ do_signal_stop        \_ claude ...
706625  689358  688328  688328 TNl+ do_signal_stop            \_ mcp-atlassian ...
---- pane ----
Claude Code has been suspended. Run `fg` to bring Claude Code back.
Note: ctrl + z now suspends Claude Code, ctrl + _ undoes input.
---- tty ----
susp = ^Z isig icanon iexten echo ...
```

What each suggested key did:

| Typed | Effect |
|---|---|
| `fg` Enter | echoed into the cooked line buffer; nothing read it; group still `T` |
| `kg` Enter | same |
| Ctrl+\_ | echoed as `^_`; same |
| Ctrl+Z again | SIGTSTP to a group that is already stopped; no change |

`kill -CONT -688328` (the throwaway's foreground group) restored it fully. Claude Code went back
to raw mode, repainted, and the buffered `fg`/`kg` lines were not submitted as a prompt.

<!-- doc:region name="root_cause" kind="replaceable" -->

## Root Cause

Claude Code reads Ctrl+Z in raw mode (`-isig`), restores the terminal and sends SIGTSTP to its
own process group. In an `ai c` pane that group is the terminal's foreground group: the child
body, its watcher, Claude Code and all its MCP servers. All of it stops.

The message's advice assumes an interactive job-control shell is waiting to take the terminal
back. In an `ai c` pane there is none. The supervisor is a non-interactive `set +m` shell in a
background process group, blocked in `wait`, and `wait` in a shell without job control does
not return for a stopped child. Measured on this host: zsh's CHLD trap fires on the stop but
`wait` keeps blocking; bash's CHLD trap fires erratically (`run_pending_traps: bad value`) and
`wait` keeps blocking too. So every process that could read the pane is stopped, and the one
process still running never learns that anything happened.

Neither tmux nor the terminal is at fault. Key pass-through was fine: the keys arrived and were
echoed. tmux does continue its own stopped pane process (the direct child), but the stopped
group here is a grandchild in a group the supervisor promoted, so tmux never sees it.

## Rejected Hypotheses

| Hypothesis | Check | Result |
|---|---|---|
| tmux key mapping or pass-through swallowed the keys | tty capture after each key | Rejected: every key arrived and was echoed in cooked mode |
| The supervisor could notice the stop with a CHLD trap | `set +m` probe under zsh and bash | Rejected as a fix: zsh `wait` does not return; bash's trap is unreliable |
| Unbind Ctrl+Z in Claude Code | grep of the 2.1.283 binary for a suspend keybinding action | None exists, and `~/.claude/keybindings.json` is global, so it would change non-`ai c` sessions too |
| Run Claude Code with SIGTSTP ignored | Claude Code sends the signal itself after handling the key | Not pursued: it would depend on the runtime keeping an inherited disposition, and it would still not cover an editor Claude Code spawns in the foreground |

## Fix

Undo the stop from outside the stopped group. Ctrl+Z in an `ai c` session is now effectively a
no-op: the session flashes its suspend notice and comes back within about a second.

- **In-pane watchdog** (`session_script.SUSPEND_WATCHDOG_SNIPPET`). Each child body starts a
  small stdlib Python loop that moves into its own process group (or the same SIGTSTP would
  stop it), stays in the session so `tcgetpgrp` on `/dev/tty` works, and once a second checks
  whether the terminal's foreground group is stopped. If it is, it sends that group SIGCONT and
  logs `ai-cli: resumed process group N, which Ctrl+Z had stopped` to the session's launch log.
  It exits when the child body is gone (checked by pid, since a `uv run` shim can sit between
  them) or when the terminal goes away. It lives in the child body rather than the supervisor
  because the supervisor is never re-exec'd. A running session therefore picks the watchdog up
  at its next agent restart after `ai update`. A supervisor-side watchdog would only ever reach
  newly created panes.
- **Launcher, on re-attach** (`main._resume_suspended_panes`). `ai c <n>`, `ai c -r`, the `ai ls`
  picker and `ai attach` continue any pane foreground group of the session that is stopped,
  before attaching. This covers a session that is found already stopped: one started from an
  older template, or one whose watchdog died.
- **Reconciled with AI-CLI-2139** (`main._settle_stopped_cc_session`). See below.

Cost: one Python process per session, waking once a second to read `/proc/<pgid>/stat` and make
one `tcgetpgrp` call. On a host without `/proc` (macOS) the state read is one `ps` per second.

## Relationship to AI-CLI-2139

AI-CLI-2139 made the launcher treat a state-`T` session process as abandoned and end it
(SIGTERM, SIGCONT, bounded wait, SIGKILL). State `T` covers two different situations, and the
terminal tells them apart:

- **Stopped while its group still owns its terminal's foreground**: suspended in place, still
  what its pane shows. This bug. It is resumed and stays in use.
- **Stopped with no terminal foreground**: nothing is attached to it. That is 2139's case, and it
  is still reclaimed exactly as before. The 2139 suite passes unchanged.

Before this fix, the 2139 path would have ended a Ctrl+Z'd session if anything checked its name's
liveness while it was stopped, which is the same outage by another route. The frozen
reconciliation test reproduced that.

## Round 2: liveness races under load

A full-suite run with `-n 4` at `9e27683` failed one test, the 2139 reconciliation one:
`left in state 'Z', not resumed`, with the launcher reporting
`pid 2333083 was present in state T, not gone. Ended it and everything it wrapped`. It passed
serially. Ending a stopped session is this bug's outage, so it was treated as a product defect
until proved otherwise. Three separate races turned up.

**1. The fixture stopped its process before the process had a terminal (fixture).**
`pty.fork()` returns in the parent before the child has called `setsid()` and taken the pty
as its controlling terminal. The fixture sent SIGSTOP as soon as `/proc` showed the child
running, which is immediately. A fork-then-stop probe of that exact pattern, 300 attempts on an
idle host:

| Child at the moment it stopped | Count |
|---|---|
| leads its own terminal's foreground (what the test meant) | 116 |
| still in the parent's group, no terminal (`tty_nr 0`, `tpgid -1`) | 163 |
| own session, no terminal yet | 21 |

A stopped process with no terminal is 2139's case, so the launcher ending it was correct for
the process the fixture actually built. Serial runs passed because the 50 ms poll usually let
the child finish `login_tty` first. The fixture now waits until the child has exec'd `sleep` and
its group is its terminal's foreground.

**2. The decision was made on a stale reading (product).** The liveness walk classifies a
record's process as stopped, and the Ctrl+Z path then read the process again to decide between
resume and reclaim. The in-pane watchdog continues a suspended group on its own schedule. When
it won that gap, the resume check saw a running process and declined, and the fallback
reclaimed it: frozen red as
`test_given_suspended_session_continued_after_liveness_classified_it_when_checked_then_not_ended`,
which at `9e27683` printed `pid ... was present in state S, not gone. Ended it`. The fix
(`main._settle_stopped_cc_session`) reads the state once more, from the same probe that
classified it, and that one reading decides: running means in use, unreadable means left alone,
and only a process still stopped and not suspended in place is reclaimed. The group and the
terminal's foreground it is paired with do not change across a Ctrl+Z or a SIGCONT (nothing in
the pane has job control to move them), so the decision still describes one moment. Using the
probe rather than `/proc` directly keeps macOS and Windows on 2139's existing path.

**3. A launcher run from a terminal "resumed" a process in its own group (product).** Run from
an interactive shell, the launcher's process group is its terminal's foreground, and so is any
process it forked. `test_given_stopped_session_in_the_callers_own_process_group_...` in the 2139
suite therefore failed from a terminal (`resumed process group N`) and passed under xdist,
whose workers have no terminal. Ctrl+Z stops the whole group, and the launcher reading this is
in that group and running, so a stopped process there was not suspended in place. It is
excluded and reclaimed. Frozen as
`test_given_stopped_session_in_a_terminal_launchers_own_group_when_checked_then_reclaimed_not_resumed`,
which runs its launcher on a pty of its own so the result does not depend on the runner.

**What cannot be told apart.** A process stopped before it has attached to any terminal looks
exactly like one with no terminal at all (`tty_nr 0`), so it is still reclaimed as 2139's case.
In an `ai c` pane that state does not occur: Claude Code is in the pane's foreground group long
before anyone can press Ctrl+Z.

**Also fixed on the way.** The first verification run failed an unrelated test,
`test_stale_session_reaper.py::..._child_receives_signal_and_stdin[bash]`
(`['INT', 'READ=hello'] == ['READ=hello', 'INT']`). The test sent SIGINT once the events file
existed, but `printf ... >>` creates the file before writing the line. It now waits for the line.
